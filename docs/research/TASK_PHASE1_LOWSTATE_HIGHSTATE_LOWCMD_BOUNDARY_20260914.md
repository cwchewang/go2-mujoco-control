## Source-level observation motivating the checkpoint

Before editing anything, verify these call-chain facts against the current source and record exact file/line references in `RESULTS.md`:

- `simulate/src/unitree_sdk2_bridge.h::RunLockstep()` publishes a state snapshot once per lockstep state tick.
- `PublishStateSnapshot()` publishes LowState using the blocking lowstate lock, while HighState is published through an independent `trylock()` path.
- The controller receives LowState and HighState through separate DDS subscribers/callbacks.
- `LowStateMessageHandler()` copies LowState under `state_mutex_` and then feeds the lockstep writer gate with `msg->tick()`.
- `HighStateMessageHandler()` independently replaces the cached HighState under the same mutex.
- `TrotExperiment::SnapshotState()` copies the latest cached LowState and HighState together under the mutex.
- `LowCmdWrite()` then computes the command from that snapshot and publishes LowCmd followed by the lockstep ack.

This architecture creates a concrete candidate: the same LowState tick may be paired with a different HighState generation/age across repetitions. This is a hypothesis to test, not a conclusion. Do not “fix” the HighState path in this task.

## Research question

At the first repeated-run LowCmd divergence, which is the earliest differing boundary?

1. the canonical state payload generated by the bridge;
2. the canonical payload received by the controller subscriber(s);
3. the exact LowState + HighState tuple copied by `SnapshotState()` and consumed by that LowCmd cycle;
4. the pre-publish LowCmd generated from an identical consumed input tuple.

The task succeeds when this boundary is localized reproducibly. It does **not** require a repair.

## Pairwise analysis

Compare all three pairs aligned primarily by consumed LowState tick / control update, never by wall-clock time.

At each update compare in this causal order:

1. bridge-source canonical LowState;
2. bridge-source canonical HighState and HighState source-generation tick / publish-skip state;
3. controller-received LowState;
4. controller-received HighState / receipt generation;
5. exact LowState + HighState tuple consumed by `SnapshotState()`;
6. pre-publish LowCmd.

The primary detector is exact byte/hash identity. When a hash differs, decode/compare canonical fields and report the first differing field plus both values and numeric delta where meaningful.

Do not call a downstream difference causal if an earlier boundary differs.

## Classification rules

Use exactly one top-level label for the checkpoint:

- `BRIDGE_SOURCE_INPUT_DIVERGENCE`: the canonical LowState or HighState generated/published by the bridge differs first for the same aligned source tick/generation.
- `HIGHSTATE_PUBLICATION_PAIRING_DIVERGENCE`: bridge physical/source data are equivalent at the aligned LowState tick, but HighState publication skip/generation causes the controller to pair that LowState with a different HighState generation.
- `TRANSPORT_OR_SUBSCRIBER_DIVERGENCE`: bridge-source canonical payload is identical, but controller receipt/cache differs before `SnapshotState()`.
- `CONTROLLER_INPUT_PAIRING_DIVERGENCE`: received stream contents are individually consistent, but `SnapshotState()` consumes a different LowState/HighState generation pairing for the same control update.
- `CONTROLLER_INTERNAL_DIVERGENCE`: the complete consumed LowState + HighState tuple is exact-equal, but pre-publish LowCmd differs.
- `NO_DIVERGENCE_IN_WINDOW`: all inspected boundaries remain identical throughout the preregistered interval.
- `INSTRUMENTATION_PERTURBATION`: diagnostic instrumentation changes protocol/baseline behavior enough to invalidate attribution.
- `PROTOCOL_FAILURE`: frozen-handoff / lockstep / provenance invariants fail.
- `UNRESOLVED_BOUNDARY`: evidence is internally inconsistent or insufficient to order the first difference.

If pair classifications disagree, the top-level result is `UNRESOLVED_BOUNDARY`; do not majority-vote a cause.
