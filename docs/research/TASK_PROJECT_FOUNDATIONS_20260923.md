# 项目基础与可接手工作方式

父提交：fd91d4613d7bd970946840344cfae8af1edcf064。
模式：治理与文档。负责人：当前 Codex 执行者，项目方向由用户决定。
用户指令：先把基础、规范、思路搞好，让 Luna 或人工也能顺利高质量推进，
暂不钻具体工作。该指令覆盖本轮入口/规范修订，不覆盖策略选型、调参或实验。

## 问题和决策

此前执行规则较完整，但“为何选这个问题/参数”和人工接手步骤不够明确；
治理页仍写旧 Phase 2 及禁止 RL 接入，README 与 CURRENT 的阶段提示也不一致。
本任务决定：如何让一个不依赖聊天历史的执行者准确识别目标、边界及下一步。

采用一份推进指南、一份短任务模板，复用现有 CURRENT/SOP/PROJECT_RECORD；
不增加另一套状态数据库、调度器、模型分工或固定审批层。依据是现有入口冲突
和已发生的“工程默认项被放到科学验收位置”的问题，不是提前选择下一份策略。

## 范围与完成依据

允许整理 maintained 入口、规范、模板及当前任务状态。保留运行代码、已封存
协议、原始实验及 FAIL 不变；不改动作/模型/阈值，不运行新物理步进。
完成时接手者能回答：项目目标是什么、当前可做什么、任务参数依据在哪里、
结果意外时怎么办、下一条动作是什么。相关文档能互相链接，生成入口一致，
变更范围确为文档/导航。无须重新 native qualification 或创设性能验收线。

验证方式：阅读冲突检查、三个交接场景的文档走查、现有质量和导航检查、
变更范围审查、PR/主线 CI。走查不是实际 Luna 或用户实测；不据此保证任何
执行者永远不会犯错。若发现运行实现才能解决的问题，记录缺口，不偷偷扩展本轮。
