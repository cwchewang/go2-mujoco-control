# 项目推进指南

给手动操作者和任何模型使用。目标是让接手者知道为什么做、做什么、做到哪里，
不靠聊天记忆或执行者临场补齐研究设计。本页解释工作方式，不保存当前状态；
当前授权与下一步只跟随 [CURRENT](../CURRENT.md) 的任务。

## 先建立正确认识

项目目标和科学结论以 [PROJECT_RECORD](PROJECT_RECORD.md) 为准；选题依据以
[TOPIC_AUDIT](TOPIC_AUDIT.md) 为准。当前控制器、速度、地形、checkpoint 都是
实现或研究变量，不自动成为项目目的。“已经接好”“上游默认”“论文有演示”
分别不能替代能力复现、选型比较、具体权重与实验的对应关系。

基础建设的完成标准是可接手、可验证、可纠偏。每条规范应防止一个真实错误，
并有明确适用范围；删去重复抄写和无助于决策的形式要求，不追求文件数量。

## 十分钟接手

在 native WSL 的 canonical checkout 中操作。当前机器位置见 workspace
START_HERE；仓库 [AGENTS](../AGENTS.md) 给出安全同步规则。

```sh
git fetch origin --prune
git status --short --branch
git rev-parse HEAD origin/main
git show origin/main:CURRENT.md
```

沿 CURRENT 读取任务和结果，再按任务需要读 PROJECT_RECORD；选题变化才需读
TOPIC_AUDIT。分支不符、存在他人改动或分叉时保留现场，先弄清所属任务，不 reset。
不需要通读历史报告。首次接手必须能用自己的话回答：本任务解决什么决策、
允许改变什么、怎样判完成、下一步具体做什么。任务里没有答案就补齐缺口，
不要从旧脚本、模型名字或聊天片段猜默认值。

## 按影响选择流程

| 工作 | 必需信息与检查 | 何时结束 |
|---|---|---|
| 文档、导航、治理 | 当前问题、改动范围、链接/生成一致性和可理解性检查 | 入口无冲突，接手者能正确说明边界 |
| 工程修复 | 可重现缺陷、允许改动、相关回归；按 CONTRIBUTING 判断是否完整资格验收 | 缺陷修复且相关检查通过 |
| 离线分析 | 固定输入、方法、输出、能回答与不能回答的问题；保持 raw 不变 | 结果可复算，结论边界明确 |
| 能力复现、探索或确认实验 | 任务决策依据、前瞻协议、预算、有效性规则及 SOP 的执行准入 | 按预声明规则收束，不临时追到通过 |

文档修改不重跑物理实验或整套 native 验收。常规任务只维护一个短任务记录；
小修复可用已有任务或 PR 描述，不为每次编辑新建任务、分支、评审和报告。
科学/执行独立审查用于 SOP 指定的语义和执行边界，不要求日常每一步找两个模型。

## 决策先于执行

任务的第一句话应说明“这个结果将帮助我们决定什么”。随后说明它怎样推进
项目目标、为什么现在做，以及当前更便宜的证据是否已经足够。不需要为已决定
的小修复重新研究路线。涉及方法、权重、benchmark 或阈值选择时，使用
[任务模板](research/TASK_TEMPLATE.md) 中的决策字段，把理由写在当前任务里。

选择方案时，区分“方便接入的起点”“等待原条件复现的候选”和“经比较选定的
主基线”。记录来源、适用范围、相关替代方案、成本和证据缺口；不要求穷举所有
方法。选择强度必须与已有证据相称，不能让已投入的工程成本代替选型依据。

选择速度、地形、样本量、阈值时，说明其来自实际需求、上游复现协议还是待验证
的工程假设。假设可以用于探索，但要标明且限制结论。先讲问题再定通过线；
没有依据的常数不能升级为全项目门槛。以往 0.15 m/s 是一个局部兼容性要求，
不是科研总目标；其历史 FAIL 保留，不倒改阈值，也不要求未来任务围绕它调参。

性能比较前先区分原条件复现与迁移到本平台，列明模型、reset、观测、动作、
控制频率和任务条件的差异。只有这些差异受控，比较才能支撑相应结论。
把 PASS、性能 FAIL、无效/基础设施失败分别会导致的下一步写清楚；验证策略
不是“无论什么结果都继续当前路线”。

## 让执行者有明确自由度

执行者可在已授权范围内自行查资料、修复实现、补相关检查和整理文档，不为
可逆的小步骤反复确认。用户授权跟随具体任务，不因换模型、换人或换会话失效。
尚未决定的科研目标、主要比较对象、信息条件、预算或通过语义，不能由执行者
悄悄补成事实；先记录候选与缺口，把需要用户取舍的具体问题提出，同时推进
不依赖该决定的工作。没有新增实验授权时，准备工作不隐含启动许可。

遇到新发现时先判断：它是执行缺陷、证据缺失，还是推翻研究假设。执行缺陷
可以在任务边界内修；影响科学问题、预算或主结论的变化应先更新任务并做相应
审查。停止受影响步骤，不把无关工作全部卡住，也不增加替代实验掩盖失败。

## 证据与结论对齐

测试通过只证明被测试的工程行为。固定输入回放只证明这些输入上的一致性。
原条件复现、平台移植成功、统计可靠性和因果解释各需对应证据；仿真不能替代
实机。报告主张时给出条件、原始证据位置与必要局限，不把候选原因写成根因。
完整 FAIL 可产生有效科学信息；无效运行不能拿来证明方法不好。
具体不可改写规则由 [SOP](research/SOP.md) 统一维护。

## 留下一个可继续的现场

结束前在当前任务或结果中写清：完成了什么、依据在哪里、哪些问题未决、下一条
可执行动作、预期产物、停止边界。写明实际分支/SHA、dirty 状态和失败/待运行项；
路径指向原文件，不复制协议。更新 docs/research/current.json 后用现有生成器
同步入口；只有科学结论/方向变化才更新对应 canonical 文件。

人工或 Luna 接手时，用三个问题检查这份交接：能否找到当前入口；能否判断
一条旧命令现在是否允许执行；能否在结果不符合预期时知道保存什么、停止什么。
答不出就修交接，不默认靠更强模型补救。这是文档可用性检查，不等同于实机或
Luna 已完成实测，也不需要每次机械生成一份新报告。

## 按需使用命令

以下命令从仓库根目录执行，不启动实验。缺少环境时按
[README](../README.md) 安装独立开发工具；不往冻结运行环境加开发依赖。

```sh
.substrate/dev-venv/bin/python -m tools.check_quality --style
python3 -m tools.research.workspace --check
git diff --check
```

编辑 current.json 后先运行 `python3 -m tools.research.workspace` 重新生成
CURRENT；上面的 --check 是检验，不是修复。质量检查只读取 Git 跟踪的文件，
新文件需在检查前加入暂存区；暂存不代表允许提交未审查内容。
构建、测试、实验持共享锁，资格验收自身持锁，不能重复套锁。具体命令与参数
跟随 [CONTRIBUTING](../CONTRIBUTING.md)、[substrate 指南](../tools/substrate/README.md)
及当前任务；本指南不提供可误点启动旧 campaign 的命令。
